## ЧАСТЬ 3: ТЕОРИЯ — Что такое MLOps? (15 минут)

### Определение MLOps

> **MLOps** = **ML** (Machine Learning) + **Ops** (Operations)
>
> Это набор практик и инструментов которые отвечают на вопрос:
> **"Как запустить ML-модель в production и оставить её там работать?"**
>
> Если **Data Scientist** говорит: "Я создал модель которая предсказывает с accuracy 92%"  
> То **ML Engineer** говорит: "Я запустил эту модель, и она работает 24/7, и я вижу что там происходит"

---

### Три столпа MLOps

#### 1. REPRODUCIBILITY (Воспроизводимость)

**Определение:**
> Один и тот же код + одни и те же данные = одна и та же модель (всегда)

**Пример:**
```bash
# День 1
$ make train
Epoch 1: loss=0.523
Epoch 2: loss=0.401
...
Final ROC-AUC: 0.785

# День 2 (месяц спустя, на другой машине)
$ make train
Epoch 1: loss=0.523
Epoch 2: loss=0.401
...
Final ROC-AUC: 0.785  ← ОДИНАКОВО!
```

**Почему это важно?**
- ✅ Вы можете экспериментировать (меняете параметр, запускаете снова)
- ✅ Вы можете доказать что модель улучшилась (не плацебо)
- ✅ Вы можете вернуться в прошлое (какие параметры были месяц назад?)
- ✅ Другие могут повторить ваш результат

**Как достичь:**
- 🔒 Зафиксировать seed: `random_state=42`
- 🔒 Зафиксировать версии пакетов: `requirements.txt`
- 🔒 Зафиксировать данные: `dvc add data/`
- 🔒 Зафиксировать параметры: `params.yaml`

---

#### 2. MONITORING (Мониторинг)

**Определение:**
> Видеть что происходит с моделью в production (сейчас и историю)

**Что мониторить?**

**Метрики сервиса:**
```
- Requests Per Second (RPS): сколько запросов в секунду?
- Latency: как быстро отвечает? (< 100 ms норма)
- Error Rate: сколько ошибок? (< 0.1% норма)
- HTTP 500: сервис упал?
```

**Метрики модели:**
```
- ROC-AUC: качество модели (была 0.85, стала 0.72 — ALARM!)
- Data Drift: данные изменились? (новые категории? новые распределения?)
- Model Drift: модель становится хуже? (постоянно растут ошибки?)
```

**Пример дашборда Grafana:**
```
┌────────────────────────────────────────┐
│  RPS        │  Latency p95  │  Errors  │
│  125 req/s  │  42 ms        │  0.02%   │
├────────────────────────────────────────┤
│     ROC-AUC TIMELINE                   │
│  0.85 ▁█████▃▂▂▁▂▃▂▁▂▂▁▂▂▂▂▂▂▂▂ 0.68  │
│  ↑ неделю назад          сейчас ↓     │
│         ("что произошло?")             │
└────────────────────────────────────────┘
```

**Почему это важно?**
- 🚨 Вы узнаете о проблеме когда она происходит (не когда клиент позвонит)
- 🔍 Вы знаете что менялось (может быть данные? может быть сервер?)
- 🚀 Вы можете быстро среагировать (откатить модель, переобучить, etc)

---

#### 3. AUTOMATION (Автоматизация)

**Определение:**
> Система сама делает то что обычно делает человек вручную

**Примеры:**

```
Вручную (в 2000-х):
1. Получить письмо "переобучить модель"
2. Скачать новые данные с сервера
3. Запустить jupyter notebook
4. Посмотреть что качество выросло
5. Сохранить модель
6. Коммитить в git
7. Собрать Docker образ
8. Развернуть на production
9. Проверить что всё работает
Время: 2 часа ручной работы, риск ошибок: ВЫСОКИЙ
```

```
Автоматически (сейчас):
1. Система видит что ROC-AUC упал
2. Система сама:
   - Скачивает новые данные
   - Запускает make train
   - Проверяет что качество выросло
   - Если выросло: ставит новую модель в production
   - Если не выросло: откатывает обратно
3. Команда читает лог: "Model updated: 0.72 → 0.78"
Время: 5 минут, риск ошибок: МИНИМАЛЬНЫЙ
```

**Как достичь:**
- ⚙️ CI/CD: GitHub Actions проверяет код на каждый коммит
- ⚙️ Scheduler: Prefect запускает переобучение по расписанию
- ⚙️ Triggers: переобучение запускается когда данные задрейфили
- ⚙️ Auto-deploy: новая модель автоматически ставится на production

## ЧАСТЬ 5: ПРИМЕРЫ ИЗ РЕАЛЬНОЙ ЖИЗНИ (12 минут)

### Пример 1: Почему нельзя забыть про random_state

**История из Яндекса:**

> Менеджер просит Data Scientist'а Петра:
> "Петр, мы внедрили твою модель в production. Но качество сбавилось на 3%. Почему?"
>
> Петр проверяет:
> - Данные: те же
> - Параметры: те же
> - Code: то же
> - Результат: РАЗНЫЙ!
>
> Почему? Потому что в коде есть:
> ```python
> # ❌ random_state не установлен!
> train, test = train_test_split(X, y, test_size=0.2)  # каждый раз разные строки!
> ```
>
> На его машине просто повезло, что random.seed() был установлен где-то ещё.
> На сервере не было. Результат: разные данные в тесте → разные метрики.

**Правильно:**
```python
# ✅ Зафиксировали seed везде
np.random.seed(params["seed"])
train, test = train_test_split(X, y, test_size=0.2, random_state=params["seed"])
```

### Пример 2: Когда забыли про params

**История из стартапа:**

> Компания предсказывает клиентам количество денег которое они потратят.
>
> Модель месяц работала отлично. Потом босс просит:
> "Поменяй threshold с 0.5 на 0.6"
>
> Data Scientist начинает искать:
> - Может в `train.py`? Нет...
> - Может в `inference.py`? Может быть...
> - Может жёстко забит в Docker образе? Вероятно...
>
> Тратит 2 часа на поиск. Находит в трёх местах! Меняет все. Забывает в одном месте.
> Результат: разные пороги в разных местах = ошибки.

**С MLOps:**
```yaml
# params.yaml
evaluate:
  threshold: 0.5  ← один файл!
```

Меняешь одну строчку — всё работает.

## ✨ KEY TAKEAWAYS

**3 главные идеи которые должны запомниться:**

1. **Production-ready code это не просто код который работает**  
   Это код который:
   - Работает везде (не только на вашей машине)
   - Работает долго (месяцы, годы)
   - Работает надёжно (вы знаете что происходит)

2. **MLOps — это инженерия, а не наука**  
   - Наука: "может ли это работать?"
