# 3. Версионирование данных и пайплайны

*Читать перед занятиями 4–5. 25 минут.*

## Проблема

Git отлично версионирует текст. Для бинарных файлов он устроен плохо:
хранит **каждую версию целиком**, а не разницу. Датасет на 200 МБ,
изменённый пять раз, — это гигабайт в репозитории, причём навсегда:
история не чистится обычными средствами.

Не версионировать данные тоже нельзя: метрика 0.79 без ответа
на вопрос «на каких данных» — бесполезное число.

## Идея: отделить содержимое от ссылки на него

DVC решает это так: в Git едет маленький текстовый файл с **хешем**
и размером, а сами данные лежат в отдельном хранилище.

```yaml
# data/raw/churn.csv.dvc — вот что попадает в Git
outs:
- md5: a1b2c3d4e5f6...
  size: 214748364
  path: churn.csv
```

Такое хранилище называется **content-addressable**: файл лежит
не по имени, а по хешу своего содержимого. Отсюда два полезных свойства:

* одинаковые файлы хранятся один раз, сколько бы копий вы ни делали;
* изменение файла автоматически меняет его адрес, подделать версию нельзя.

Это тот же принцип, на котором устроена объектная база самого Git.

## Что даёт связка Git + DVC

```bash
git checkout HEAD~5     # вернулись к коду пятинедельной давности
dvc checkout            # вернулись к данным, которые тогда были
```

Git отвечает на вопрос «какой был код», DVC — «какие были данные».
Воспроизводимость требует обоих ответов одновременно.

## Remote — где физически лежат данные

Хранилище может быть каким угодно: папка на диске, S3, MinIO,
Google Drive, SSH-сервер. Команды `dvc push` и `dvc pull` работают
одинаково — по аналогии с `git push`/`git pull`.

Важное правило: remote должен быть **вне рабочей копии репозитория**.
Иначе данные вернутся в Git через чёрный ход.

Секреты доступа к хранилищу пишутся в `.dvc/config.local`, который
не коммитится, — тот же принцип, что и с `.env`.

## Пайплайн как граф

Второй крупный механизм DVC — описание процесса в виде графа стадий.

```yaml
stages:
  prepare:
    cmd: python -m src.data.prepare
    deps: [src/data/prepare.py, data/raw/churn.csv]
    outs: [data/processed/train.csv]
  train:
    cmd: python -m src.train
    deps: [src/train.py, src/features.py, data/processed/train.csv]
    params: [seed, train]
    outs: [models/model.joblib]
```

Каждая стадия объявляет: что запускать (`cmd`), от чего зависит (`deps`,
`params`) и что производит (`outs`). Выход одной стадии становится
входом другой — так и строится граф.

**Зачем это нужно.** DVC хеширует все зависимости и запоминает результат.
При `dvc repro` он пересчитывает только то, что реально устарело:
поменяли `learning_rate` — переобучение без перегенерации данных.

Это отвечает на вопрос, который иначе держится в голове: «я изменил
одну строчку, что нужно перезапустить?» Ответ теперь даёт инструмент,
а не память.

## Самая опасная ошибка занятия

**Забыть зависимость в `deps`.**

Если `src/features.py` не указан в зависимостях стадии `train`,
то при изменении препроцессора DVC решит, что ничего не поменялось,
и переиспользует старую модель.

Ошибки не будет. Будет **неверный результат**, который выглядит
как верный. Это опаснее падения: падение вы заметите сразу.

## Метрики в пайплайне

Метрики объявляются отдельно от обычных выходов:

```yaml
    metrics:
      - reports/eval_metrics.json:
          cache: false
```

`cache: false` означает «не убирай этот файл в хранилище DVC,
пусть лежит прямо в Git». Файл маленький, а взамен работает
сравнение между коммитами:

```bash
dvc metrics diff HEAD~1
```

Вы получаете разницу метрик между версиями кода без ручных таблиц.

## Что версионировать, а что нет

| Артефакт | Где | Почему |
|---|---|---|
| Код | Git | текстовый, нужна история построчно |
| Конфиги | Git | текстовые, нужны в ревью |
| Метрики (JSON) | Git | маленькие, нужно сравнение между коммитами |
| Сырые данные | DVC | большие, бинарные |
| Обработанные данные | DVC (или пересчитывать) | выводимы из сырых |
| Модели | DVC или реестр моделей | большие, бинарные |
| Секреты | ни там, ни там | переменные окружения |

Отдельный вопрос — нужно ли версионировать промежуточные данные.
Если пайплайн быстрый, их проще пересчитывать. Если обучение идёт
часами, дешевле хранить.

## Частые заблуждения

**«DVC — это замена Git».** Нет, это дополнение: DVC работает поверх Git
и без него бесполезен.

**«DVC хранит diff данных».** Нет, он хранит версии целиком, просто
не в Git. Экономия — за счёт дедупликации одинаковых файлов,
а не за счёт дельт.

**«Раз есть пайплайн, эксперименты не нужны».** Разные задачи:
пайплайн отвечает «как воспроизвести», трекинг (занятие 6) — «что получилось».

**«`.dvc`-файл можно не коммитить».** Тогда пропадает вся польза:
именно он связывает версию кода с версией данных.

## Вопросы к зачёту, которые закрывает конспект

* Что именно делает `dvc add` с файлом и что попадает в Git
* Чем `dvc repro` отличается от перезапуска скрипта, как DVC понимает, что стадию можно пропустить
* Почему модель нельзя хранить в Git, что хранить вместо неё
