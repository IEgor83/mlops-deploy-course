# 5. Тестирование ML-систем

## Проблема

В обычном коде ошибка вызывает исключение. Вы видите стектрейс
и чините. В ML-коде ошибка вызывает **правильно оформленный
неправильный ответ**.

Классический пример: сдвиг таргета на одну строку.

```python
df["churn"] = df["churn"].shift(1).fillna(0).astype(int)
```

Пайплайн отработает. Модель сохранится. Метрики запишутся. Всё зелёное.
ROC-AUC упадёт до 0.52, но никто на это не смотрит — ведь ничего не упало.
Узнают через месяц по жалобам бизнеса.

Отсюда главный принцип: **тест отвечает не на вопрос «упало ли»,
а на вопрос «осмысленно ли то, что получилось»**.

## Что тестировать: четыре группы

| Группа | Вопрос | Пример |
|---|---|---|
| Данные | пришло ли то, что мы ожидаем | доля оттока в пределах 5–60 % |
| Препроцессинг | корректно ли обработаны граничные случаи | неизвестная категория не роняет transform |
| Поведение модели | осмысленна ли модель как модель предметной области | больше жалоб → выше риск оттока |
| Контракт API | правильно ли сервис реагирует на некорректный вход | мусор → 422, не 500 |

### Тесты данных

Данные — вход системы, и они портятся чаще кода: изменился формат
выгрузки, добавилась категория, поехала кодировка.

Что проверяют:

* **схема** — все ожидаемые колонки на месте, типы верные;
* **диапазоны** — стаж не отрицательный, вероятность в [0, 1];
* **пропуски** — их доля не выросла внезапно;
* **дубликаты** — один клиент не встречается дважды;
* **вырожденность таргета** — защита от «все нули»;
* **детерминизм** — одинаковый сид даёт одинаковые данные.

Для сложных случаев есть специальные библиотеки (pandera, Great
Expectations), описывающие схему декларативно. В курсе достаточно pytest.

### Поведенческие тесты модели

Здесь главное отличие от обычного тестирования: мы **не можем**
проверить точное значение выхода. Оно зависит от данных, сида,
версии библиотеки.

Но мы можем проверить свойства, которые обязана иметь любая адекватная
модель этой задачи.

**Направленные тесты** — изменение признака двигает предсказание
в известную сторону:

```python
# больше обращений в поддержку -> выше риск ухода
assert proba(angry_customers).mean() > proba(calm_customers).mean()
```

Если это правило нарушено — где-то перепутаны колонки или знак.

**Инвариантные тесты** — изменение, которое не должно влиять,
не влияет: перестановка колонок, порядок строк в батче.

**Минимальная функциональность** — модель не выродилась:
предсказания в [0, 1], дисперсия не нулевая, метрика выше порога.

Эта классификация (invariance / directional / minimum functionality)
пришла из работы CheckList для NLP, но работает для любых моделей.

### Тесты контракта

Граница системы: коды ответов, валидация, формат.
Проверяют, что мусор на входе даёт понятный 422, а не 500,
и что в ответе есть версия модели.

## Порог в тесте: как не сделать мигающий тест

Плохо:

```python
assert roc_auc > 0.79     # а получилось ровно 0.79
```

Такой тест начнёт падать от смены версии sklearn, и через месяц
его отключат.

Хорошо:

```python
assert roc_auc > 0.70     # ловим катастрофу, а не колебания
```

Тест должен ловить поломку (0.5 — модель сломана), а не шум
в третьем знаке. Для отслеживания медленной деградации есть
quality gate в `evaluate.py` и мониторинг.

## Скорость тестов

Тесты, которые идут четыре минуты, не запускают. Главный приём —
обучать модель один раз на всю сессию:

```python
@pytest.fixture(scope="session")
def trained_pipeline(...):
    ...
```

И второй: тесты не должны зависеть от того, запускал ли кто-то пайплайн.
Данные генерируются в фикстуре, а не читаются из `data/processed/`.
Иначе тест «работает у меня» и падает в CI.

## Пирамида тестов в ML

Классическая пирамида (много юнит-тестов, мало интеграционных)
работает и здесь, но с поправкой: появляется отдельный слой
проверок данных, которых в обычной разработке нет.

```
        /\        ручная проверка на защите
       /  \       интеграционные (сервис + модель + стенд)
      /____\      поведенческие тесты модели
     /______\     юнит-тесты кода и препроцессинга
    /________\    валидация данных
```

Нижний слой самый дешёвый и ловит больше всего проблем.

## Чего тесты не ловят

Важно понимать границы. Тесты проверяют, что **код правильный**.
Они не заметят:

* что мир изменился и данные поехали (это мониторинг, занятие 15);
* что модель хуже конкурента (это A/B-тест);
* что задача поставлена неверно.

Зелёные тесты означают «система работает как задумано»,
а не «система приносит пользу».

## Частые заблуждения

**«Покрытие 100 % значит, что всё хорошо».** Покрытие меряет,
сколько строк выполнилось, а не сколько проверено по существу.
Двадцать тестов вида `assert result is not None` дадут высокое
покрытие и нулевую защиту.

**«Тестировать модель бессмысленно, она же вероятностная».**
Тестируются свойства, а не значения.

**«Хватит тестов на код, данные проверять не нужно».**
Наоборот: данные ломаются чаще кода.

**«Если тест иногда падает, увеличим порог».** Мигающий тест —
симптом. Либо в системе есть недетерминизм, либо порог выбран неверно.
