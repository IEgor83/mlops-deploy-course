# Как получить обновления курса, не потеряв свою работу

В методички занятий 4–17 добавлены новые требования. Ниже — как их
забрать безопасно.

## Короткий ответ: скорее всего, ничего делать не нужно

Методички — это **документация**. Откройте их на GitHub и читайте:

https://github.com/alsu124/mlops-deploy-course/tree/main/lessons

Ваш проект и репозиторий курса — разные вещи. Сливать один в другой
не требуется, и в большинстве случаев этого делать не стоит.

Обновление нужно только если вы хотите держать методички у себя локально.

---

## Перед любым обновлением

```bash
git status
```

Если есть незакоммиченные изменения — сначала сохраните их:

```bash
git add -A
git commit -m "Сохранить работу перед обновлением"
git push
```

Правило простое: **закоммиченное вернуть можно всегда, незакоммиченное — нет.**

## Определите свой случай

```bash
ls
```

**Случай А — в списке есть `template/`, `lessons/`, `docs/`.**
Вы склонировали репозиторий курса целиком и работаете внутри `template/`.

**Случай Б — в списке `src/`, `tests/`, `params.yaml`, а `lessons/` нет.**
У вас отдельный проект. Это правильный вариант.

## Случай Б: отдельный проект

Делать не нужно ничего. Методички читаете на GitHub по ссылке выше.

Ваш репозиторий содержит только ваш проект — так и должно быть.

---

## Случай А: копия курса

### Чем опасно обычное `git pull`

Ваши решения лежат в `template/src/train.py`, `features.py`, `prepare.py`.
В репозитории курса эти же файлы — **заготовки с TODO**. Обычный `git pull`
попытается их слить, и вы получите конфликт прямо в решённых файлах.
В худшем случае, разрешив конфликт не в ту сторону, потеряете работу.

Ещё опаснее `docs/`. Вы создаёте там свои документы по заданиям:
`runbook.md`, `model-card.md`, `slo.md`, `model-promotion.md`.
Забрав `docs/` из курса целиком, вы их сотрёте.

### Безопасный способ: забрать только методички

```bash
# 1. Добавить репозиторий курса вторым источником (один раз)
git remote add upstream https://github.com/alsu124/mlops-deploy-course.git

# 2. Скачать его содержимое, ничего не меняя у себя
git fetch upstream

# 3. Посмотреть, что изменилось в методичках
git diff --stat HEAD upstream/main -- lessons/

# 4. Забрать ТОЛЬКО папку lessons/ — свой код и docs/ не трогаем
git checkout upstream/main -- lessons/

# 5. Зафиксировать
git add lessons/
git commit -m "Обновить методички из репозитория курса"
git push
```

Шаг 4 — ключевой. `git checkout upstream/main -- lessons/` меняет
ровно одну папку. `template/`, `src/`, `docs/`, ваши отчёты
и история остаются нетронутыми.

**Никогда не делайте** `git merge upstream/main` или
`git checkout upstream/main -- .` — это и есть тот случай,
когда работа теряется.

### Проверьте, что ничего не пропало

```bash
git status
git log --oneline -3
```

Ваши файлы должны быть на месте:

```bash
grep -c "" template/src/train.py     # ваш решённый файл, не заготовка
ls docs/                             # ваши runbook.md и прочие на месте
```

### Нужен ли для этого Pull Request

**Нет.** Обновление методичек — это не изменение вашего кода, ревьюить
здесь нечего. Коммитьте прямо в `main`, как показано выше.

Но если на занятии 2 вы включили защиту ветки, `git push` может
отказать:

```
remote: error: GH006: Protected branch update failed for refs/heads/main.
```

Это значит, что защита работает — так и задумано. Два пути.

**Путь 1. Через ветку и PR** (правильный, займёт минуту):

```bash
git switch -c chore/update-lessons
git checkout upstream/main -- lessons/
git add lessons/
git commit -m "Обновить методички из репозитория курса"
git push -u origin chore/update-lessons
```

Дальше на GitHub: Compare & pull request → Create → Merge.

Если в защите стоит «Require approvals: 1», кнопка Merge может
быть недоступна: одобрить собственный PR нельзя. Вы владелец
репозитория и администратор, поэтому под кнопкой будет ссылка
вида «merge without waiting for requirements» — это допустимо
для технического обновления, но **не привыкайте так делать
с обычными задачами**: смысл защиты именно в том, чтобы код
кто-то посмотрел.

**Путь 2. Попросить напарника.** Вы всё равно ревьюите друг друга
по заданию занятия 2 — пусть заодно нажмёт Approve здесь. Это дольше,
зато честно и попадёт в вашу историю PR как ещё один пример.

### Если вы ещё не дошли до занятия 2

Значит, защиты ветки у вас нет и PR вам пока не нужен вообще.
Команды из предыдущего раздела сработают как есть: коммит в `main`
и `git push`.

## Обновления будут повторяться

Методички правятся по ходу курса: где-то яснее формулировка, где-то
новое требование. Это нормальная жизнь учебных материалов, а не аврал.

**Как узнаете.** Преподаватель напишет в чат группы. Отдельно следить
не нужно.

Если хотите видеть изменения сами — на странице репозитория курса
кнопка **Watch → Custom → галочка Pushes**. Тогда GitHub пришлёт
уведомление на почту при каждом обновлении. Это по желанию.

**Что делать во второй и последующие разы.** Подключать `upstream`
заново не нужно, он уже настроен. Остаются три команды:

```bash
git fetch upstream
git checkout upstream/main -- lessons/
git add lessons/ && git commit -m "Обновить методички" && git push
```

Посмотреть, что именно изменилось, до того как забирать:

```bash
git fetch upstream
git diff --stat HEAD upstream/main -- lessons/
```

**Что обновление не трогает никогда.** Папку `lessons/` — и только её.
Ваш код в `src/` или `template/src/`, ваши документы в `docs/`,
отчёты, история коммитов остаются как были. Это свойство команды
`git checkout upstream/main -- lessons/`, а не обещание: она физически
не может изменить ничего за пределами указанного пути.

## Если всё-таки что-то сломалось

Ничего не потеряно, пока есть история Git.

```bash
git reflog
```

Найдите строку с состоянием до обновления и вернитесь:

```bash
git reset --hard HEAD@{1}
```

Если не получается — напишите преподавателю **до** того, как будете
чинить дальше. Чем меньше действий сделано после поломки, тем проще
восстановить.
