# Runbook: что делать дежурному

Эталонный пример. Студенты пишут свой на занятиях 14–16;
здесь — образец глубины, которую вы от них ждёте.

Принцип: каждый раздел отвечает на три вопроса — как убедиться,
что проблема реальна; что сделать сейчас; когда эскалировать.

## ServiceDown — сервис недоступен

**Симптом:** `up{job="churn-api"} == 0` дольше минуты.

1. `docker compose ps` — контейнер `api` в состоянии `Up`?
2. Если `Exited` — `docker compose logs --tail=100 api`, искать последний стектрейс.
3. Частые причины: не найден `models/model.joblib` (том не смонтирован),
   занят порт 8000, OOM при старте на машине с 4 ГБ.
4. `docker compose up -d api` для перезапуска.

**Эскалация:** сервис не поднимается после двух перезапусков —
откатиться на предыдущий образ: `docker run ghcr.io/<repo>:<предыдущий тег>`.

## ModelNotLoaded — процесс жив, модели нет

**Симптом:** `model_loaded == 0` дольше двух минут. `/predict` отвечает 503.

1. `curl -s localhost:8000/health` — посмотреть `model_version`.
2. Если пусто — проверить MLflow: `curl -s localhost:5000/health`.
3. Если MLflow жив, проверить, что в реестре есть версия в стадии `Production`.
4. Если MLflow недоступен — должен был сработать фолбэк на локальный файл;
   его отсутствие означает, что `models/` не смонтирован в контейнер.
5. Починив источник, дёрнуть `curl -X POST localhost:8000/reload`.

**Почему critical:** сервис отвечает кодом 503 на каждый запрос —
для потребителя это полный отказ, хотя контейнер выглядит здоровым.

## HighLatencyP95 — p95 выше 500 мс

**Симптом:** держится дольше пяти минут.

1. Открыть дашборд: выросло ли RPS одновременно с latency?
   Если да — это нагрузка, а не деградация.
2. `docker stats` — упёрлись в CPU?
3. Посмотреть разбивку по эндпоинтам: если растёт только `predict_batch`,
   значит кто-то шлёт батчи под 1000 объектов — это ожидаемо.
4. Разовое лечение: увеличить число воркеров uvicorn.

**Эскалация:** если p95 растёт при неизменном RPS — это регрессия,
искать в последнем релизе.

## HighErrorRate — больше 5 % ошибок

1. `docker compose logs --tail=200 api | grep -c "ошибка предсказания"`.
2. Если ошибки однотипны — смотреть, какое поле приходит некорректным.
   Скорее всего, поменялся формат данных на стороне потребителя.
3. Отличать 422 от 500: 422 означает, что клиент шлёт мусор
   (проблема на их стороне), 500 — что наш код не справился.

**Порог 5 % выбран так:** при штатной работе доля ошибок близка к нулю;
единичные 422 от кривых интеграций дают доли процента. 5 % —
это уже система, а не случайность. Порог 1 % давал бы ложные срабатывания
при подключении нового потребителя, 20 % — слишком поздний сигнал.

## PredictionDistributionShift — сдвинулось распределение предсказаний

**Симптом:** медиана предсказанной вероятности за час отличается
от суточной больше чем на 0.15.

Это не отказ, а сигнал посмотреть.

1. `make drift` — построить отчёт Evidently на свежих данных.
2. Открыть `reports/drift.html`: какие признаки дрейфуют?
3. Проверить, не сбой ли это выгрузки: посмотреть долю пропусков
   и число строк в свежих данных. Дрейф из-за битой выгрузки —
   самая частая ложная тревога.
4. Если данные корректны и дрейф реален — см. следующий раздел.

## Обнаружен дрейф данных

Дрейф — не команда переобучать, а повод разобраться.

**Проверить, что это не ложная тревога:**
* объём свежих данных не меньше 1000 строк;
* доля пропусков не выше обычной;
* дрейфуют признаки, которые модель реально использует,
  а не второстепенные;
* нет ли сезонного объяснения (акция, праздник, запуск тарифа).

**Когда переобучать:** дрейф подтверждён, и качество на размеченных
данных упало ниже `evaluate.min_roc_auc`.

**Как:** `dvc repro`, затем сравнить новую модель с текущей продовой
**на одной и той же тестовой выборке**. Промоутить только при приросте
ROC-AUC не менее 0.005.

**Кто решает:** промоут в `Production` выполняет владелец сервиса,
а не дежурный. Дежурный собирает данные и заводит задачу.

## Автопереобучение промоутнуло плохую модель

1. В MLflow перевести предыдущую версию обратно в `Production`,
   текущую — в `Archived`.
2. `curl -X POST localhost:8000/reload`, проверить `model_version` в `/health`.
3. Остановить flow: `prefect deployment pause`.
4. Разобраться, почему сравнение пропустило модель: скорее всего,
   сравнивали на разных данных или `min_gain` слишком мал.

Откат занимает минуты — именно ради этого модель живёт в реестре,
а не в файле рядом с кодом.
