# Занятие 13. CD и релизы

## Проблема

Заказчик хочет посмотреть на ваш сервис. Что вы ему скажете?
«Установи Python 3.11, клонируй репозиторий, поставь зависимости,
настрой DVC, скачай данные, обучи модель, запусти uvicorn»?

Цель занятия — чтобы ответ звучал так:

```bash
docker run -p 8000:8000 ghcr.io/ваш-логин/ваш-репо:1.0.0
```

## Шаг 1. CI и CD — разные вещи

| | CI | CD |
|---|---|---|
| Когда | на каждый PR | на тег релиза |
| Вопрос | «можно ли это мержить?» | «выкатываем» |
| Результат | зелёный/красный чек | опубликованный артефакт |

Поэтому это отдельный workflow с другим триггером.

## Шаг 2. Workflow публикации

`.github/workflows/cd.yml`:

```yaml
name: CD

on:
  push:
    tags: ["v*"]

permissions:
  contents: read
  packages: write

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Подготовить модель для образа
        run: |
          pip install -r requirements.txt
          python -m src.data.generate --n 8000
          python -m src.data.prepare
          python -m src.train --no-mlflow
          python -m src.evaluate

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha

      - uses: docker/build-push-action@v5
        with:
          context: .
          file: docker/Dockerfile
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

Ключевые места:

**`permissions: packages: write`** — без этой строки публикация упадёт
с `denied: permission_denied`. `GITHUB_TOKEN` создаётся автоматически,
заводить свой секрет не нужно.

**`metadata-action`** сам расставляет теги: из `v1.2.3` получатся
`1.2.3`, `1.2` и тег по хешу коммита. Тег `1.2` удобен тем, кто хочет
получать патчи автоматически.

**Обучение модели перед сборкой.** Модель в `.gitignore`, поэтому
в раннере её нет — её нужно получить. В учебном проекте обучаем на месте;
в реальном сюда встал бы `dvc pull` или загрузка из Registry.

**`cache-from: type=gha`** — кэш слоёв между прогонами, экономит минуты.

## Шаг 3. Проверка образа до публикации

Публиковать непроверенный образ нельзя. Добавьте шаг после сборки:

```yaml
      - name: Проверить образ
        run: |
          IMAGE=$(echo "${{ steps.meta.outputs.tags }}" | head -1)
          docker run -d --name check -p 8000:8000 "$IMAGE"
          for i in $(seq 1 20); do
            sleep 2
            curl -sf localhost:8000/health && break
          done
          curl -sf localhost:8000/health | grep -q '"model_loaded":true'
          docker rm -f check
```

Цикл с ожиданием обязателен: контейнер стартует не мгновенно,
а `curl` сразу после `docker run` получит отказ соединения.

## Шаг 4. Первый релиз

```bash
git tag -a v1.0.0 -m "Первый релиз: сервис предсказания оттока"
git push origin v1.0.0
```

Смотрите вкладку Actions. По завершении — вкладка Packages в профиле
репозитория: там ваш образ.

Сделайте пакет публичным: Package settings → Change visibility → Public.
Иначе никто не сможет его скачать без токена.

Проверьте, что получилось:

```bash
docker pull ghcr.io/ваш-логин/ваш-репо:1.0.0
docker run --rm -p 8000:8000 ghcr.io/ваш-логин/ваш-репо:1.0.0
curl -s localhost:8000/health | jq
```

## Шаг 5. Версионирование

Семантическое версионирование `MAJOR.MINOR.PATCH`:

| Что изменилось | Версия | Пример |
|---|---|---|
| Ломающее изменение API | MAJOR | убрали поле из ответа |
| Новая возможность, обратно совместимая | MINOR | добавили `/predict/batch` |
| Исправление | PATCH | починили обработку пропусков |

Теперь главный вопрос занятия: **вы переобучили модель, код не менялся.
Какая версия?**

Ответ: это две разные оси, и путать их нельзя.

* **Версия сервиса** (`v1.2.0`) отвечает за контракт: какие эндпоинты,
  какие поля, какие коды ответов.
* **Версия модели** (`churn-classifier v7` в Registry) отвечает за качество
  предсказаний.

Именно поэтому вы на занятии 10 возвращаете `model_version` в теле ответа
отдельно: потребитель должен различать «сервис обновился» и «модель обновилась».

Практическое следствие: переобучение модели в схеме с Registry
**вообще не требует релиза сервиса** — достаточно промоута версии и `/reload`.

## Шаг 6. Release notes

На GitHub: Releases → Draft a new release → выберите тег `v1.0.0`.

Опишите по-человечески:

```markdown
## Что нового
- Сервис предсказания оттока: /predict, /predict/batch, /health
- Модель: gradient_boosting, ROC-AUC 0.79 на отложенной выборке
- Порог классификации 0.42, подобран по PR-кривой

## Как запустить
docker run -p 8000:8000 ghcr.io/логин/репо:1.0.0

## Известные ограничения
- Максимум 1000 объектов в батче
- Модель зашита в образ; для обновления без пересборки используйте MLflow Registry
```

Раздел «Известные ограничения» не формальность: он экономит часы поддержки.

## Шаг 7. Взаимная проверка

Обменяйтесь с соседом ссылками на образы и запустите чужой.
Если чужой сервис не поднялся или не отвечает на `/health` — разберитесь
вместе почему. На зачёте будет ровно эта процедура, только с оценкой.

## Шаг 8. Что именно вы выкатили

### Опись содержимого образа (SBOM)

Через полгода выйдет уязвимость в библиотеке, и первый вопрос будет:
«она у нас в проде есть?» Ответить «сейчас соберу образ и посмотрю»
нельзя — тот образ собирался из других версий.

SBOM (Software Bill of Materials) — список всего, что попало в образ,
приложенный к релизу.

```yaml
      - name: Собрать SBOM
        uses: anchore/sbom-action@v0
        with:
          image: ${{ steps.meta.outputs.tags }}
          format: spdx-json
          output-file: sbom.spdx.json

      - name: Приложить SBOM к релизу
        uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.spdx.json
```

Теперь на вопрос про уязвимость отвечает `grep` по файлу, а не пересборка.

### Гейт на размер образа

Образ имеет свойство расти незаметно: кто-то добавил зависимость,
кто-то закомментировал строку в `.dockerignore`. Через полгода
вместо 400 МБ — два гигабайта, и никто не знает когда.

```yaml
      - name: Проверить размер образа
        run: |
          IMAGE=$(echo "${{ steps.meta.outputs.tags }}" | head -1)
          SIZE=$(docker image inspect "$IMAGE" --format='{{.Size}}')
          MB=$((SIZE / 1024 / 1024))
          echo "размер образа: ${MB} МБ"
          test "$MB" -lt 500 || { echo "образ вырос больше 500 МБ"; exit 1; }
```

Тот же принцип, что у quality gate по метрике на занятии 3: деградацию
ловит автоматика, а не человек через полгода.

## Полезное

| Команда | Зачем |
|---|---|
| `git tag -a v1.0.0 -m "..."` | создать аннотированный тег |
| `git push origin v1.0.0` | отправить тег (обычный push теги не отправляет) |
| `git tag -d v1.0.0` | удалить локально |
| `git push origin :refs/tags/v1.0.0` | удалить в удалённом репозитории |
| `docker pull ghcr.io/...` | скачать опубликованный образ |
