# Занятие 14. Мониторинг сервиса — план

**Цель:** студент видит, что происходит с сервисом, и получает сигнал
до того, как о проблеме сообщит пользователь.

**Артефакт:** `/metrics`, Prometheus собирает, дашборд Grafana в репозитории,
минимум один осмысленный алерт с описанием действий.

## Тайминг

| Мин | Что |
|---|---|
| 0–10 | Проверка ДЗ: релиз v1.1.0, откат |
| 10–25 | Демо: сервис «работает», но не работает |
| 25–75 | Работа |
| 75–85 | Нагрузка на свои сервисы, смотрим графики вживую |
| 85–90 | ДЗ |

## Демо (10–25 мин)

Подготовьте сервис, в котором модель не загрузилась (уберите
`models/model.joblib` из образа). Запустите его:

```bash
docker compose ps        # api  Up (healthy?)
```

Спросите: «Сервис работает?» Процесс жив, порт слушает, `docker ps`
зелёный. А `/predict` возвращает 503 на каждый запрос.

Вывод, который нужно проговорить: «процесс запущен» и «сервис работает» —
разные утверждения. Мониторинг существует, чтобы измерять второе.

Дальше покажите живой дашборд под нагрузкой:

```bash
while true; do curl -s -o /dev/null -X POST localhost:8000/predict \
  -H 'Content-Type: application/json' -d @examples/request.json; done
```

## Четыре золотых сигнала — на доску

| Сигнал | Метрика в нашем сервисе |
|---|---|
| Latency | `prediction_latency_seconds` |
| Traffic | `rate(prediction_requests_total[1m])` |
| Errors | доля `status="error"` |
| Saturation | загрузка CPU/памяти контейнера |

Плюс специфичная для ML пятая: **распределение предсказаний**.
Гистограмма `prediction_probability` — дешёвый детектор дрейфа
прямо в проде: сдвиг медианы виден за часы, а падение бизнес-метрик —
за недели. Это подводка к занятию 15.

## Что объяснить обязательно

**Counter против Histogram.** Counter только растёт, из него считают
скорость через `rate()`. Histogram копит распределение по корзинам,
из него считают перцентили через `histogram_quantile()`.

**Почему p95, а не среднее.** Среднее время ответа 100 мс при том, что
5 % пользователей ждут 3 секунды, — это плохой сервис со «хорошей» метрикой.
Нарисуйте распределение с хвостом.

**Алерт без инструкции — мусор.** Каждое правило в `alerts.yml` должно
содержать аннотацию `action`: что делать дежурному. Иначе алерт разбудит
человека, который не знает, что предпринять, и через месяц его отключат.

**Порядок отладки: снизу вверх.** Пустой график в Grafana отлаживают так:
`curl /metrics` → Prometheus Targets → Prometheus запрос → дашборд.
Начинать сверху — терять время.

## Типовые ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Пустой график | Prometheus не видит цель | Status → Targets, там причина |
| Prometheus: `connection refused` | указан `localhost:8000` | В compose — `api:8000` |
| `histogram_quantile` даёт NaN | нет данных в окне | Создать нагрузку, увеличить окно |
| Метрики есть, но не растут | метрика создаётся внутри функции | Объявлять на уровне модуля |
| Дашборд не сохранился | правили в UI без экспорта | Экспортировать JSON в репозиторий |

## Нагрузка (75–85)

Каждый создаёт нагрузку на свой сервис и показывает соседу графики.
Задача: объяснить, что означает каждая линия и почему p99 выше p50.

## Ключевая мысль

> Сервис без мониторинга не «работает» — про него просто ничего не известно.
