# Занятие 2. Git для ML-команды — план

**Цель:** студент работает через ветки и PR, а не коммитит в `main`;
`pre-commit` не пускает мусор в репозиторий.

**Артефакт:** смерженный PR с ревью однокурсника, зелёный `pre-commit`.

## Тайминг

| Мин | Что |
|---|---|
| 0–10 | Проверка ДЗ: у всех ли `make train` и `EXPERIMENTS.md` |
| 10–25 | Демо: показываю, как выглядит репозиторий, куда закоммитили модель и данные |
| 25–70 | Работа в парах: ветка → PR → ревью → мерж |
| 70–85 | Разбор конфликтов и ошибок |
| 85–90 | ДЗ |

## Демо (10–25 мин)

Заготовьте репозиторий-антипример: туда закоммичены `model.joblib` (50 МБ),
`data/raw/*.csv`, `.env` с токеном и три файла `train_v2.py`, `train_final.py`,
`train_final_НОВЫЙ.py`.

Покажите на нём:

```bash
git count-objects -vH        # размер репозитория
git log --oneline            # "fix", "fix2", "работает", "не удалять"
git log -p -- .env           # токен виден в истории даже после удаления файла
```

Последнее — главный момент занятия. Удаление файла из рабочей копии
**не удаляет его из истории**. Отсюда правило: секрет, попавший в Git,
считается скомпрометированным и подлежит отзыву, а не удалению.

## Что объяснить обязательно

**Почему модели и данные не место в Git.** Git хранит полную копию каждой
версии бинарного файла. Пять версий модели по 50 МБ — репозиторий на 250 МБ,
который клонируется минутами и никогда не уменьшится. Это подводка к DVC
на занятии 4: скажите прямо, что решение будет через две недели.

**Зачем PR, если работаешь один.** Два аргумента, оба честные: PR — это точка,
куда цепляется автоматическая проверка (занятие 9), и это способ описать
изменение так, чтобы через полгода понять, зачем оно было.

## Работа в парах (25–70)

Разбейте группу на пары. Каждый добавляет второго в коллабораторы своего
репозитория. Дальше циклом:

1. A создаёт ветку `feature/add-model-selection`, пушит, открывает PR.
2. B ревьюит: минимум один комментарий по существу (не «ок»).
3. A правит, B аппрувит, A мержит.
4. Меняются ролями.

Требование к ревью: комментарий должен указывать на конкретную строку
и предлагать, что сделать. «Мне не нравится» ревью не считается.

## Типовые ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `pre-commit` переписал файлы и коммит «не прошёл» | это нормальное поведение: хук исправил и остановился | `git add -u && git commit` ещё раз |
| В PR 40 изменённых файлов | закоммичены `__pycache__`, `.venv` | Проверить `.gitignore`, `git rm -r --cached` |
| `check-added-large-files` блокирует коммит | пытается закоммитить модель | Так и задумано. Это подводка к занятию 4 |
| Конфликт в `params.yaml` | оба правили один файл | Разбирайте на проекторе — конфликт в YAML показателен и безопасен |
| Студент коммитит прямо в `main` | привычка | Включите branch protection в его репозитории вместе с ним |

## Если успели раньше

Дать задание: найти в своей истории коммит, который делает две несвязанные вещи,
и объяснить, почему это плохо. Показать `git rebase -i` не нужно —
достаточно осознания.
