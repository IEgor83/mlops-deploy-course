# Занятие 4. Версионирование данных: DVC — план

**Цель:** данные и модели выведены из Git в DVC; `dvc pull` восстанавливает
их на чистом клоне.

**Артефакт:** `.dvc`-файлы в Git, remote настроен, `dvc push`/`dvc pull` работают.

## Тайминг

| Мин | Что |
|---|---|
| 0–10 | Проверка ДЗ: `model_meta.json`, таблица экспериментов |
| 10–25 | Демо: боль → инструмент |
| 25–75 | Работа: init, add, remote (локальный), затем MinIO |
| 75–85 | Разбор |
| 85–90 | ДЗ |

## Демо (10–25 мин)

Порядок обязателен: **сначала боль, потом DVC.**

```bash
# 1. Сгенерируйте большой датасет
python -m src.data.generate --n 2000000
ls -lh data/raw/churn.csv        # ~200 МБ

# 2. Попробуйте закоммитить
git add -f data/raw/churn.csv
git commit -m "данные"
git count-objects -vH
```

Вопрос группе: «А теперь я меняю в файле одну строку и коммичу снова.
Сколько будет весить репозиторий?» Покажите: ещё +200 МБ. Git хранит
не дельту бинарника, а новую копию.

Второй вопрос: «Хорошо, не коммитим. Тогда как коллега получит
те же самые данные, на которых я обучил модель?» Варианты из зала —
почта, диск, папка на сервере — разберите каждый: ни один не связывает
версию данных с версией кода.

Только теперь вводите DVC одним предложением:

> DVC кладёт в Git не файл, а его отпечаток; сам файл живёт в хранилище.
> Отпечаток версионируется вместе с кодом — и `git checkout` старого коммита
> вместе с `dvc checkout` возвращает те самые данные.

Покажите на проекторе содержимое `.dvc`-файла — там всего несколько строк.

## Про remote: два шага, не один

Сначала **локальный** remote (папка вне репозитория) — чтобы механика была
понятна без сети:

```bash
dvc remote add -d localremote /tmp/dvcstore
```

Только когда у всех заработало — MinIO как S3-совместимое хранилище.
Если поднять MinIO сразу, половина группы будет отлаживать эндпоинты
вместо понимания DVC.

## Типовые ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `dvc push` кладёт всё обратно в репозиторий | remote указан внутрь рабочей копии | remote должен быть **вне** репозитория |
| `output 'data/raw/churn.csv' is already tracked by Git` | файл был закоммичен раньше | `git rm -r --cached data/raw/churn.csv`, затем `dvc add` |
| `dvc pull` ничего не тянет | забыли `dvc push` | Проверить `dvc status -c` |
| MinIO: `SignatureDoesNotMatch` | не задан `endpointurl` | `dvc remote modify minio endpointurl http://localhost:9000` |
| В Git попал `.dvc/cache` | не сработал `.gitignore` от `dvc init` | `.dvc/cache` и `.dvc/tmp` игнорируются, проверить |

## Ключевая мысль

> Git отвечает на вопрос «какой был код», DVC — «какие были данные».
> Воспроизводимость требует обоих ответов одновременно.

## Если успели раньше

Задание: сделать два коммита с разными версиями данных, затем
`git checkout <старый> && dvc checkout` и убедиться, что файл вернулся
к прежнему содержимому. Это единственный способ по-настоящему понять DVC.
