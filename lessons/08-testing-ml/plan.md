# Занятие 8. Тестирование ML-систем — план

**Цель:** студент понимает, что в ML-проекте тестируется не только код,
и умеет писать тесты данных и поведенческие тесты модели.

**Артефакт:** `make test` зелёный, ≥ 8 осмысленных тестов в четырёх группах.

## Тайминг

| Мин | Что |
|---|---|
| 0–10 | Проверка ДЗ: `scripts/promote.py` |
| 10–25 | Демо: сломанный пайплайн, который не падает |
| 25–75 | Работа |
| 75–85 | Разбор: чьи тесты ловят подложенную поломку |
| 85–90 | ДЗ |

## Демо (10–25 мин)

Самая сильная демонстрация курса. Заготовьте копию проекта, в которой
в `prepare.py` таргет случайно сдвинут на одну строку:

```python
df["churn"] = df["churn"].shift(1).fillna(0).astype(int)
```

Запустите на проекторе:

```bash
dvc repro
```

Всё зелёное. Пайплайн отработал, модель сохранилась, метрики записались.
ROC-AUC упал до 0.52 — но никто на это не смотрит, потому что **ничего не упало**.

Вопрос группе: «В обычном бэкенде сломанный код падает. Почему здесь нет?»

Ответ, к которому подводите: ML-система деградирует **тихо**. Она не
выбрасывает исключение — она начинает выдавать неправильные ответы
в правильном формате. Значит проверять нужно не «не упало ли»,
а «осмысленно ли то, что получилось».

## Четыре группы тестов — на доску

| Группа | Что проверяет | Пример |
|---|---|---|
| Данные | схему, диапазоны, пропуски, дубликаты | доля оттока в пределах 5–60 % |
| Препроцессинг | обработку граничных случаев | неизвестная категория не роняет transform |
| Поведение модели | инварианты предметной области | больше звонков в поддержку → выше риск оттока |
| Контракт API | коды ответов, валидацию | мусор на входе → 422, не 500 |

Про поведенческие тесты скажите отдельно: мы не можем проверить точное
значение выхода, но можем проверить **направление реакции**. Если модель
на увеличение числа жалоб отвечает снижением риска оттока — где-то
перепутаны знаки или колонки.

## Типовые ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Тесты идут 4 минуты | модель обучается в каждом тесте | Фикстура `scope="session"` |
| Тест требует запущенного пайплайна | читает `data/processed/train.csv` | Генерировать данные в фикстуре |
| `assert roc_auc > 0.9` | нереалистичный порог | Порог — чуть ниже текущего результата, иначе тест будет мигать |
| Тест на точное значение метрики | зависит от версии sklearn | Проверять свойства, не числа |
| 20 тестов, все на `assert not None` | имитация покрытия | Спросить: какую поломку ловит этот тест? |

## Проверка в конце (75–85)

Раздайте всем один и тот же «сломанный» diff (сдвиг таргета) и попросите
применить его у себя. Чьи тесты покраснели — у того тесты работают.
У кого зелено — обсуждаем, какого теста не хватило.

## Ключевая мысль

> В ML тест отвечает не на вопрос «упало ли», а на вопрос
> «осмысленно ли то, что получилось».
