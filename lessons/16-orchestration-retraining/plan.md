# Занятие 16. Оркестрация и автопереобучение — план

**Цель:** замкнуть петлю: дрейф → переобучение → сравнение → промоут → `/reload`.

**Артефакт:** Prefect-flow, отрабатывающий все три сценария
(дрейфа нет / есть, но модель не лучше / есть, модель лучше).

> **Занятие необязательное.** При потере пар из-за праздников снимается
> первым. Даёт +4 бонусных балла к итоговому проекту (см. `docs/assessment.md`).
> Если снято — выдать методичку на самостоятельное изучение.

## Тайминг

| Мин | Что |
|---|---|
| 0–10 | Проверка ДЗ: таблица деградации, ответ про автопереобучение |
| 10–25 | Демо: почему «переобучать по расписанию» — плохая идея |
| 25–75 | Работа |
| 75–85 | Разбор: чей flow корректно отверг плохую модель |
| 85–90 | ДЗ |

## Демо (10–25 мин)

Начните с ответов на четвёртый вопрос ДЗ занятия 15.
Соберите сценарии, когда автопереобучение делает хуже:

* дрейф из-за сбоя выгрузки — переобучились на битых данных;
* сезонный всплеск (чёрная пятница) — переобучились на аномалии
  и потеряли качество на обычных днях;
* новые данные ещё без меток — переобучение на неполной разметке;
* модель переобучилась и стала хуже, но её всё равно выкатили.

Отсюда формулировка правила занятия:

> Переобучать не по расписанию, а по причине.
> И промоутить только если стало лучше.

Покажите эталонный flow и все три исхода: `skipped`, `rejected`, `promoted`.

## Что объяснить обязательно

**Зачем оркестратор, если есть cron.** Cron запускает команду. Оркестратор
даёт: граф зависимостей, повторные попытки, историю прогонов,
видимость где именно упало, параметры запуска. На одной задаче разница
незаметна, на десяти — принципиальна.

**`min_gain` — не перестраховка.** Разница ROC-AUC в 0.001 между двумя
обучениями — это шум. Промоут по такому «улучшению» означает случайную
замену модели в проде. Порог прироста делает решение осмысленным.

**Ошибка сравнения.** Новую и старую модель нужно сравнивать
на **одних и тех же** данных. Сравнить старую метрику из отчёта трёхмесячной
давности с новой, посчитанной на свежем тесте, — популярная и грубая ошибка.

**Prefect против Airflow.** Скажите честно: в индустрии чаще Airflow,
но он требует БД, шедулера и веб-сервера — полчаса пары уйдёт на подъём.
Prefect запускается как обычный Python и даёт те же понятия.
Кто хочет Airflow — в домашнем задании есть вариант.

## Типовые ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Flow промоутит всегда | нет сравнения со старой моделью | Добавить `current_production_metrics` |
| Сравнение на разных данных | новая метрика с нового теста | Фиксировать тестовую выборку |
| Flow падает на `dvc repro` | нет данных или remote | Явный `cwd`, обработка кода возврата |
| `/reload` не отвечает | сервис в контейнере, flow на хосте | Правильный URL, обработка исключения |
| Логи flow не видны | не используется `get_run_logger()` | Заменить `print` |

## Разбор (75–85)

Попросите каждого продемонстрировать сценарий `rejected` — когда flow
переобучил модель, но отказался её выкатывать. Это самая ценная часть:
студенты обычно пишут только «счастливый путь».

## Ключевая мысль

> Автоматизация — это не «делать без человека».
> Это «принимать решение по записанному правилу, а не по настроению».
