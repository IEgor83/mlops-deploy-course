# Занятие 17. Сборка проекта и репетиция защиты

Сегодня новых тем нет. Приводим проект в состояние, в котором его
можно защищать, и репетируем защиту.

## Шаг 1. Прогон чек-листа

Делаем все вместе. **В новой папке**, не в рабочей копии:

```bash
git clone <ваш-репозиторий> /tmp/check17 && cd /tmp/check17
dvc pull
docker compose -f docker/docker-compose.yml up -d
sleep 30
curl -s localhost:8000/health
curl -s -X POST localhost:8000/predict -H 'Content-Type: application/json' -d @examples/request.json
pytest -q
docker compose -f docker/docker-compose.yml down -v
```

Каждая упавшая команда — задача на сегодня. Самое частое:

| Упало | Почти всегда причина |
|---|---|
| `dvc pull` | забыт `dvc push`, или ключи remote только локально |
| `docker compose up` | пути в compose завязаны на вашу рабочую директорию |
| `/health` отвечает `degraded` | модель не попала в образ и не смонтирована |
| `pytest` | тест читает файл, которого нет в чистом клоне |

Всё это на защите означает «проект не работает».

## Шаг 2. README

README — первое и часто единственное, что читает проверяющий.
Обязательные разделы:

```markdown
# Название проекта
![CI](бейдж)

## Задача
Два предложения: что предсказываем и зачем это бизнесу.

## Архитектура
Схема стенда: сервисы, кто с кем общается, где данные, где модель.

## Быстрый старт
docker run -p 8000:8000 ghcr.io/логин/репо:1.0.0
или docker compose up -d

## Модель
Алгоритм, метрики на тесте, порог и почему такой.

## Пайплайн
dvc repro — что во что превращается.

## API
Эндпоинты, форматы запроса и ответа, коды ошибок.

## Мониторинг
Что измеряется, какие алерты, скриншот дашборда.

## Разработка
Как поднять локально, как прогнать тесты, как выпустить релиз.
```

Проверьте себя: сможет ли человек, который видит проект впервые,
запустить его, читая только README? Дайте почитать соседу.

## Шаг 3. ADR — записать решения

ADR (Architecture Decision Record) — короткая запись о том, почему
сделано так, а не иначе. Через полгода вы не вспомните причину,
а решение останется.

Создайте `docs/adr/` и напишите **три** записи по шаблону:

```markdown
# ADR-001. Загрузка модели из MLflow Registry с фолбэком на локальный файл

## Контекст
Сервису нужна актуальная модель. Registry даёт версионирование
и откат за секунды, но это внешний сервис, который может быть недоступен.

## Решение
При старте пробуем Registry (стадия Production). При любой ошибке
логируем warning и грузим models/model.joblib.

## Последствия
+ недоступность трекинг-сервера не роняет инференс
+ обновление модели не требует пересборки образа
− молчаливый фолбэк может скрыть проблему: закрыто метрикой model_loaded
  и алертом на неё

## Альтернативы
1. Только Registry — простой код, но отказ MLflow = отказ сервиса.
2. Только локальный файл — надёжно, но обновление требует пересборки.
```

Темы для остальных двух возьмите из своих решений: почему такой порог
классификации, почему в CI обучение на 4000 строк, почему mlflow и dvc
не попали в прод-образ, почему модель в образе, а не томом.

## Шаг 4. Закрыть долги

Откройте `docs/assessment.md`, раздел «Требования к итоговому проекту»,
и пройдите по чек-листу построчно. Отметьте всё, чего нет.

Приоритет, если времени мало:

1. **Блокирующее** (без этого незачёт независимо от баллов):
   зелёный CI, запуск одной командой, `dvc pull` на чистом клоне.
2. **Дорогое по баллам**: сервис и контейнер (7), мониторинг (6),
   тесты и CI (6).
3. **Косметика**: оформление README, скриншоты.

## Шаг 5. Репетиция защиты

В парах, строго по таймеру, 7 минут на человека.
Слушающий играет преподавателя: задаёт два вопроса и отмечает
чек-лист из `docs/assessment.md`.

Рабочая структура демо на 7 минут:

| Мин | Что показываете |
|---|---|
| 0:00–0:30 | Задача и что построено — два предложения, не больше |
| 0:30–1:30 | Чистый клон, `dvc pull`, `docker compose up` |
| 1:30–2:30 | Запрос в `/predict`, показ `/docs`, показ ответа с версией модели |
| 2:30–3:30 | MLflow: эксперименты, реестр, модель в Production |
| 3:30–4:30 | CI: зелёный workflow, показ падения по quality gate |
| 4:30–5:30 | Grafana: дашборд под нагрузкой, алерты |
| 5:30–6:30 | Evidently: отчёт о дрейфе, обнаруженные признаки |
| 6:30–7:00 | Итог: что бы доработали дальше |

**Главная ошибка репетиции** — четыре минуты рассказа про отток клиентов
и три минуты на всю систему. Оценивается инженерия, а не постановка задачи.

Отрепетируйте вслух хотя бы раз. Про себя не считается: вслух
всегда получается дольше, чем кажется.

## Шаг 6. Подготовка к вопросам

Откройте `docs/assessment.md`, раздел «Вопросы к зачёту».
Пройдите список и отметьте те, на которые не можете ответить уверенно.
Разберитесь с ними сегодня — на защите будет один из них.

Дополнительно будет два вопроса по вашему проекту. Готовьтесь
отвечать на «почему вы сделали именно так» по любому файлу в репозитории.

## Шаг 7. Карточка модели

ADR объясняют инженерные решения. Но на защите и в реальной работе
первым придёт вопрос от не-инженера: «что эта модель делает,
кому её можно показывать и где она врёт?»

Заведите `docs/model-card.md`:

```markdown
# Карточка модели: предсказание оттока

## Назначение
Для чего сделана, кто пользуется, какое решение принимается
по её ответу. Что она НЕ предназначена делать.

## Данные
На чём обучена, за какой период, сколько объектов,
доля положительного класса. Ссылка на паспорт данных.

## Метрики
ROC-AUC, PR-AUC, F1 на отложенной выборке. Порог и почему такой.
Метрики по сегментам — со ссылкой на reports/SEGMENTS.md.

## Ограничения
Где модель заведомо плоха. Например: на клиентах со стажем
менее месяца данных мало, качество ниже; на тарифах,
запущенных после даты обучения, поведение непредсказуемо.

## Риски
Что будет, если ошибётся в одну сторону и в другую.
Кого эти ошибки затронут сильнее.

## Обслуживание
Кто владелец, как часто переобучается, по какому сигналу,
как откатить.
```

Раздел «Ограничения» — обязательный и самый ценный. Модель без
явно названных границ применимости однажды используют там,
где она не работает, и виноват будет тот, кто её отдал без карточки.

Заполняйте по своему проекту, цифры берите из своих отчётов,
а не придумывайте.

## До зачёта

1. Выпустите финальный релиз `v1.0.0` (или выше).
2. **Скачайте всё заранее**: docker-образы, зависимости. Интернет
   в аудитории может лечь, а вы будете защищаться.
3. Последний коммит — **за сутки** до защиты. Правки утром в день
   зачёта не принимаются.
4. Возьмите ноутбук, зарядку и переходник для проектора.
